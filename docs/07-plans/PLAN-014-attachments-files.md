> **As built (2026-11-12, track D, branch `p014-s2-upload`).** Built on `c26ed55`. No new dependency (sharp, fast-check and Node's `fs`, `crypto`, `zlib.crc32` were already there). No migration, no config variable (`UPLOAD_MAX_MB` exists).
> - **Route** (`files/routes.ts`): `UPLOAD_PURPOSES` is `avatar, logo, attachment, inline`; `preview` stays `400`. One `*` content-type parser: for `attachment`/`inline` it hands the request stream to the handler unread; for everything else it buffers with the 2 MB image limit (`collect`, replacing Fastify's `parseAs: 'buffer'`, same behaviour and message). Order for the streamed purposes: `Content-Length` over `UPLOAD_MAX_MB` → `413` in `onRequest`; ready; session (`401` "Log in to upload a file."); purpose (missing or unknown: `400` with the purpose message, body unread, `Connection: close`); uploads at once (3 per user, `429`); rate (30/min bucket); caps (`unclaimedUsage`, declared length or 0); floor (free − (declared length or the limit) < 1 GiB → `507`); body; then caps and floor again after writing (actual size), name, dimensions, and in one transaction the caps under the uploader's lock, the rename and the insert. Every refusal of a streamed upload with its body unread or half-read sends `Connection: close`, so the rest isn't read for nobody. An undeclared body stops at the limit (`413`, same message). Messages (§6.4): "Files must be 25 MB or smaller." (the configured limit), "Choose a file to upload.", the floor and caps texts; the purpose refusal is now "Say what the file is for: ?purpose=attachment, ?purpose=inline, ?purpose=avatar or ?purpose=logo." Answer `201 {id, url, mimeType, size, name, width?, height?}`. Logs: `file uploaded` (`fileId`, `purpose`, `size`), `upload refused` (`reason`: `rate`, `caps`, `floor`, `busy`, `idle`); never the name or bytes.
> - **Rates:** two token buckets, `FILE_UPLOADS_PER_MINUTE` 30 and `IMAGE_UPLOADS_PER_MINUTE` 10 (`UPLOADS_PER_MINUTE` kept as the avatar alias).
> - **Receiving** (`files/upload-body.ts`, new; not in the plan's list): `receiveUpload(blobs, source, limit)` is one pull loop: count, buffer the first 8 KB, `sniffType`, then pass chunks through the stripper for the four image types, into `BlobStore.putStream`. Between reads it holds the sniff head or the stripper's one pending unit. The request is iterated with `destroyOnReturn: false`, so stopping at the limit doesn't reset the socket before the `413`. Errors: `BodyTooLarge` 413, `EmptyBody` 400, `UnreadableImage` 400 (E25), `ENOSPC`/`EDQUOT` 507 (E9), a client that went away 400 (nobody reads it).
> - **`BlobStore`** gains `putStream(source, finish?) → {tempPath, sha256, key, size}` (`<uploads>/tmp/<uuid>.tmp`, opened `wx+`, one chunk written before the next is pulled; the temp file is removed if the source throws), `commit(tempPath, key)` (always a rename, even over an existing key), `discard(tempPath)` (new, not in the plan: removes a temp file after a refusal or a failed transaction) and `getStream(key) → {stream, size}`. `commit` and `discard` refuse paths `putStream` didn't make. `finish` may return a patch (WebP's RIFF size): it is written in place and the file is read back to hash it, so the key is always the hash of the stored bytes. `memoryBlobStore` implements the same.
> - **Sniffing** (`files/sniff.ts`): as planned. `sniffType(head, complete)`: `complete` says the head is the whole body, so a cut character at the 8 KB boundary is allowed only when more follows. ZIP also matches the empty-archive and spanned markers.
> - **Stripping** (`files/strip-location.ts`): **deviation:** not a Node `Transform` but an incremental stripper (`write(chunk) → Buffer[]`, `end()`, `patch()`) driven by one generator per format, so the upload has a single read-write loop and no stream buffers in between. Beyond the plan, after looking at sharp's output: libvips writes PNG XMP as **`zTXt`**, so XMP is dropped from `iTXt`, `zTXt` and `tEXt`, plus ImageMagick's `Raw profile type exif|APP1|xmp`; JPEG extended XMP is dropped too; GIF's `XMP DataXMP` application extension is dropped; WebP's VP8X EXIF/XMP flags are cleared; bytes after each format's end are dropped (an appended image could carry its own EXIF). EXIF: the GPS pointer is looked for in IFD0 and IFD1, both byte orders; the GPS IFD's entries, out-of-line values and next pointer are zeroed (an empty IFD). Unknown TIFF types, out-of-range offsets, junk between JPEG segments, a first PNG chunk other than IHDR, a WebP chunk past the RIFF size, an unknown GIF block or any truncation are `UnreadableImage`. SPEC-014 §4.8 updated with these.
> - **Names** (`files/names.ts`): `cleanFileName` as §4.8. Clarifications: a raw (not percent-encoded) non-ASCII header is undecodable (`file`); a repeated header reaches the route as one value, since Node joins it into `"a, b"`, and is cleaned like any name (an array, which only a caller passing raw headers could give, is `file`); an "extension" over 32 bytes isn't kept when cutting; trimming dots means `.env` becomes `env`. `attachmentDisposition` and `asciiFallback` (also replaces control characters); `filename*` encodes everything outside RFC 8187 `attr-char`.
> - **Limits** (`files/limits.ts`): the §4.6 constants (GiB, matching `doctor`'s 1 GiB warning), `diskSpace(dir)` (`statfs`, `bavail × bsize`), `belowFloor`, `overCaps`. `FileRouteDeps.diskSpace` is required; `app.ts` passes `diskSpace(uploadsDir(dataDir))`.
> - **Store** (`files/store.ts`): `VisibleFile` gains `name` (for `Content-Disposition`); `unclaimedUsage(client, userId)` counts `attachment`/`inline` rows with no issue (the shape of `files_unclaimed_uploader_idx`).
> - **Dimensions** (`image.ts`): `dimensionReader(log, loadSharp)`: `sharp(path).metadata()` with no pixel limit and no decode; undefined if the header can't be read; if sharp can't load, every upload goes on without dimensions and `sharp could not load; image dimensions are left empty` is logged once (E10). `SharpFactory` input is `Buffer | string`.
> - **Download:** visibility → `stat` (missing: the missing-file `404`) → a matching `If-None-Match` is `304` with `etag` and `cache-control` only, nothing opened → `HEAD` sends the headers with an empty body, nothing opened → `GET` opens the bytes (`getStream`; gone since the `stat`: the same `404`) → only then `etag`, `cache-control`, `content-disposition`, `content-type` (`text/plain; charset=utf-8` for text), `content-length`. That fixes S1's note: a row without bytes is now the missing-file `404`, headers included. Inline only for the four image types and `preview`, never with `?download=1`.
> - **Errors:** `ROUTE_ERROR_STATUS.INSUFFICIENT_STORAGE = 507`, listed in the OpenAPI `Error` description (`packages/operations/src/catalog.ts`); SPEC-003 §9 already had it.
> - **For S3:** the insert is `withTransaction(reserveUpload, commit, insert)` with a `// S3` marker in `routes.ts`'s `storeUpload`: replace the rename and insert with `insertUpload` (key lock, rename, insert), keeping `reserveUpload` first in the same transaction. `commit` tolerates a retried transaction: when the temp file is gone and the key exists, it succeeds, so `inTransaction`'s retry on `40001`/`40P01` doesn't fail on the second rename. If the transaction throws, the route discards the temp file; a key renamed before a failed insert is left for the sweep, as §4.5 says. `<uploads>/tmp/*.tmp` is where the sweep looks. `BlobStore.delete` stays for the drain.

> - **Review fixes (2026-11-12, coordinator review: 1 blocker, 2 majors, minors and nits; each fix began with a test seen failing):**
>   - **B1, hostile structure:** a JPEG scan full of stuffed bytes, restart markers or fill bytes, a JPEG of 2 MB of fill bytes or restart markers between segments, and a GIF of 1-byte sub-blocks made per-byte work and per-byte writes. ## 3. Migration & rollback

Two migrations, both with the next migration number at the time.

- **S1 (files, `blob_release`, avatar/logo FKs).** Forward-only after release. Before the first release it rolls back by reverting the code and the migration file together (the M1 migrations are not yet released): drop the FKs, the `blob_release` table and the added `files` columns, narrow the purpose check, and cast `size` back to `integer` (safe while no file is over 2 GB). The FKs are added with no clean-up step: there are no existing users or rows, so no id can fail them (SPEC-014 D13, user decision 2026-11-12). A dev database that fails them is recreated.
- **S4a (`attachments`, `files.issue_id` FK).** Additive. Rolls back before release by dropping the table and the FK. After release the tables are kept (forward-only). It is a separate migration from S1 because `files.issue_id` can't reference `issues` until PLAN-011 S3 exists.

No data is moved. M0 file rows keep working: their `issue_id` is null and their purpose is `avatar` or `logo`.

## 5. Risks & mitigations

| Risk | Mitigation |
|---|---|
| **Lost bytes.** Rows share one key, and a delete racing a copy could unlink bytes a row still names. This is silent data loss. | Every insert and delete takes the per-key lock (S3). Bytes are unlinked only by the drain, after a re-check under the lock. The fast-check model runs in S3, and so does the Postgres half of AC-14 (Q15 exception granted 2026-11-12), since a fake lock can't show this bug. |
| **A file leaks through the uploader exception or a stale cache.** | One visibility function for `GET`, `HEAD`, `If-None-Match` and `FileRef` (S1), tested cell by cell before any attachment exists. `Cache-Control: private, no-cache` with the check done before the 304. |
| **Previews cannot be queued from a `web` role.** Today pg-boss starts in `web` only when SMTP is set. `attachment.createFile` must enqueue in its own transaction. | S4b starts the producer side of pg-boss in every role (queues created, `send` available) and leaves `work` to `all` and `worker`. If `SURFACE_ROLE=web` runs with no worker, previews wait and images show the type icon: documented in the ops notes. |
| **Memory.** Streaming bugs would hold whole files; 30 simultaneous image decodes OOM-killed the server in M0. | The 64 KB counting-stream test (S2). One shared decode limiter per process (S4b). Perf check by hand, AC-20. |
| **Location stripping corrupts images.** Hand-written JPEG, PNG and WebP chunk rewriting is easy to get wrong. | Fixtures with GPS EXIF and XMP, decoded pixels compared before and after (S2). A file that fails to parse is stored as uploaded only if it is not an image of those types; for those types a parse failure refuses the upload with the "unreadable image" message rather than storing location data. |
| **Claim vs clean-up races** (E24). | One conditional `UPDATE … RETURNING` per file, `SKIP LOCKED` in clean-up, `FOR SHARE` on the copy source, covered by AC-21 statement tests and the model in S3. |
| **Cross-plan timing.** S4a and S4b need foundations from PLAN-011 and PLAN-013. | S1–S3 are independent and ship first. S4a is built after PLAN-011 S6. The `claimInlineFiles` seam and its callers exist from PLAN-011 S6 and PLAN-013 S3, so S4b changes only the body, whichever lands first. |
| **A slow single-disk host fills up.** | The 1 GB floor and per-user caps (S2), a `blob_release` backlog metric (S3). Configurable quotas wait for M7. |
