Implements: [SPEC-015](../06-specs/SPEC-015-trash-archive.md) · Status: **Ready** (M1 acceptance gate, 2026-11-12) · Order: **after PLAN-011 S4**, last of the M1 plans to finish · Depends on: PLAN-011 S3 (`lockIssueForWrite`, groups from the issue row) and S4 (issue operations), S4c (archived and deleted issues leave the replica, for S1's optimistic and S4), S1 (`updateWhere`/`deleteWhere`), S2 (archive on the wire, `unarchive`), S5/S6 (content rows, for purge); PLAN-014 S4a (the file purge step and `purge-bytes.test.ts`, on PLAN-014 S3's `deleteFiles` and `blob_release`); PLAN-012 S1 (`whileTyping`, `ui.available`, destructive ranking), S4 (issue page, read-only frame) and S6 (delete dialog, `Mod+Z`); PLAN-010 S2 (`status.delete` handler, for S1's auto-close wiring); PLAN-013 S3/S4 and PLAN-014 S4a (their operations add lifecycle rows and purge steps)

There is no issue code yet. Everything under `issues/`, `ops/issue*.ts` and the archive screens is **new**.

### S2: Purge and the `trash-purge` job · M (2 d)

- **Purge steps** (`apps/server/src/issues/purge-steps.ts`, new): a registry of `{ model, step(tx, repo, issueId) }`, run children before parents. Every child table of `issues` has an `ON DELETE RESTRICT` FK, so a child without a step makes purge fail loudly. This slice registers the content children it knows: IssueContent and IssueHistory, deleted with `repo.deleteWhere(…, { log: false })` (PLAN-011 S1; no `D` per row, Q2). - **Comment threads (from PLAN-013 S3, which merged first and created `purge-steps.ts`):** its steps are Reaction, `comment_search_text`, then Comment with `deleteWhere(…, { childrenFirst: 'parentCommentId' })`, so replies are locked and deleted before roots and no chunk deletes a root whose reply is still there (`comments_parent_comment_id_fk` is `RESTRICT`). The chunk boundary is unit-tested in `apps/server/test/comment-purge-step.test.ts`. **⏸ Held (integration):** a Postgres thread purge, `apps/server/test/comment-purge.int.test.ts` (an issue with threads straddling a chunk boundary, purged with no error and no row left), written when the hold lifts.
- **Q2 (decided 2026-11-12):** content rows of a purged issue log no `D`. A constant `LOG_CONTENT_DELETES` in `purge-steps.ts`, `false` by default, is passed as `log` to every content step. ## 5. Risks & mitigations

| Risk | Mitigation |
|---|---|
| A new write path skips `lockIssueForWrite`, so a comment lands on a deleted issue | The table test fails if a named handler skips the lock; each later plan adds its row (PLAN-013 S3/S4, PLAN-014 S4a). |
| A new child table of `issues` has no purge step, so purge fails on the `RESTRICT` FK | `purge-steps.test.ts` reads the schema and fails when a table with an FK to `issues` has no registered step; PLAN-013 S3 and PLAN-014 S4a register theirs in the PR that adds the table. |
| Purge of a heavy issue holds the global sync lock too long | Content rows log no `D` (Q2, decided 2026-11-12); the fallback constant (`false` by default) would restore the chunked per-row log if ADR-0022 were superseded. Measured against the §10 budget once the perf hold lifts. |
| Skipping content `D`s leaves a client replica with stale content | The client drops content when the Issue is absent after a batch (PLAN-011 S5b); the sync property suite compares the replica to a fresh bootstrap after a purge. |
| The server-backed archive page shows stale rows | It refreshes on focus, after the user's own delete and restore confirmations, and on `A`, delete or restore `U` and `V` packets of a subscribed team (debounced to 1 s, `archive-source.test.ts`); restore removes the row at once. For an unsubscribed team there are no packets, so focus and the user's own actions are the triggers. |
| A restore waits for packets the connection never gets (the issue's team isn't subscribed) | The toast and the page depend on the mutation's confirmation and on `issue.get`, never on a packet (`restore-flow.test.ts`). |
| A restored issue shows no attachments | `issue.restore` logs the Attachment rows again in its transaction (S1, AC-21). |
| Jobs run twice or never (several workers, a down day) | `singletonKey` plus catch-up on start; all three jobs are idempotent and cap at 5,000 a run. |
| Auto-archive or auto-close surprises users (a big backlog archived at once) | Default 6 months, "changes apply within a day" copy, 5,000 cap spreads a large backlog over days (E19). |
| The 30-day boundary differs between client and server | One `purgeAfter` in `packages/domain`, used by both; exact-boundary tests with a fake clock. |
| Blocking dependency order: S1 needs PLAN-011 S4 and PLAN-012 S1; S4 needs PLAN-012 S4 | The slices stay mergeable because the rule table, handlers and jobs are tested with fakes; S4 is the last slice and waits for the issue page. |
| Existing nullable team columns hold rows that break the new checks | The migration backfills nulls to 6 before adding the checks. |
