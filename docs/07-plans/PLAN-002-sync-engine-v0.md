## 1. Slices

### S1: `packages/sync-protocol` · S · ✅ Done 2026-11-06
- Wire types and Zod codecs: bootstrap frames (`meta`, `row`, `end`), WebSocket messages (`deltas` with `prev` and `ack`, `resync`, `ping`/`pong`), mutate request and response.
- NDJSON stream encoder/decoder (works in a worker and in Node).
- `computeSchemaHash(modelDefs)`: a stable hash of the synced model names, fields, and types.
- **Tests:** round-trip codecs, a partial-chunk NDJSON decoder, schemaHash stability.

> **As built (2026-11-06, session D):**
> - **Deps:** `zod` ^4.6.7 (same range as the server); dev: `fast-check` ^4.10.2, `@types/node` (tests only).
> - **Structure:** `src/scalars.ts` (sync id, UUID, seq, sync group, model and op names, row), `bootstrap.ts`, `socket.ts`, `mutate.ts`, `ndjson.ts`, `schema-hash.ts`, `sha256.ts`, `errors.ts`. Each message has a Zod schema, an inferred type, and a `decode*` helper that throws `ProtocolError`. Error messages name the path and rule, never the payload, so row data can't reach logs.
> - **Portability:** `src` builds with `lib: ES2023 + WebWorker` and no Node types (`tsconfig.build.json` sets `types: []`), so a Node-only API in `src` fails `pnpm build`. Only `TextEncoder`/`TextDecoder` are used.
> - **Deviations and additions** (all in sync-protocol.md §4 and §11, handed off to A):
>   - `deltas.packets` may be empty when `ack` is non-empty. A mutation can write rows its own client cannot see, and the client must still confirm it.
>   - The WebSocket URL carries `schemaHash`, so the hub can answer `resync(schema)` (S4 needs it; the doc's URL lacked it).
>   - `SEQ_GAP` error bodies carry `lastSeq`, so the client knows where to resend from.
>   - Decoders enforce ordering: packet ids strictly increasing and > `prev`, mutation and result seqs consecutive.
>   - `presence` is left out of the codecs (M4). A message with an unknown `t` fails to decode.
> - **NDJSON:** `NdjsonDecoder` is push-based (`push(chunk)` → values, `end()`), accepts byte or string chunks (not mixed), reassembles UTF-8 split across chunks (`fatal: true`, so malformed bytes throw), tolerates CRLF and blank lines, and caps a line at 8 Mi chars. `decodeNdjson(asyncIterable)` wraps it. A push API avoids depending on `ReadableStream` async iteration in browsers.
> - **`computeSchemaHash(models: Iterable<SchemaHashModel>)`:** the input is structural: `{ name, load, fields: { [name]: { type, nullable } } }`. S6's `defineModel` output must provide these keys (extra keys such as refs and indexes are ignored). The hash is SHA-256 hex of the canonical form, using a pure-TS SHA-256 because `crypto.subtle` is missing on plain-HTTP origins. It is cross-checked against `node:crypto`. `SYNC_PROTOCOL_VERSION` (now exported from `schema-hash.ts`) is part of every hash.
> - **Tests (99):** fast-check round trips for every message type, connect params and NDJSON (byte and text chunking at arbitrary cut points), rejection cases per codec, a pinned golden hash, order independence, per-field sensitivity, FIPS vectors plus padding boundaries. Property tests use the fixed seed `PROPERTY_SEED` in `test/support/arbitraries.ts`, and fast-check prints the seed and path on failure.
> - **For later slices:** S3/S4/S5 import the schemas from `@surface/sync-protocol` (server code reads `dist/`, which the build produces). Use `decodeSocketConnectParams(request.query)`, `decodeMutateRequest(body)` and `encodeNdjsonLine(frame)`. S6 must define the canonical field `type` strings (e.g. `uuid`, `string`, `int`, `enum:a|b`), because they feed the hash.

### S2: Sync tables & repo layer (server) · L · ✅ Done 2026-11-06
- Migrations: `sync_log`, `sync_state` (seeded with 0), `client_mutations`. The `sync_groups text[] NOT NULL` convention is documented in `db/README.md`.
- `apps/server/src/sync/repo.ts`: `insert`, `update` (reads back the full row), `archive`, `unarchive`, `purge`. Each computes `groups` with a per-model `groupsOf(row, tx)` function and buffers changes.
- `flushSyncLog(tx, origin)`: `pg_advisory_xact_lock(SYNC_LOCK)`, bump `sync_state`, bulk-insert into `sync_log`. Wired into the executor (it replaces the PLAN-003 passthrough repo).

- `DebugItem` schema plus ops.
- **Tests:** an ordering stress test with 20 workers × 500 mutations, replaying `sync_log` to verify the IDs are gap-free and in commit order (AC-1); lock hold-time metric < 2 ms.

> **As built (2026-11-06).**
> - **Versions:** no new packages.
> - **Migrations:** `0004_sync_tables` (`sync_log` with the action CHECK and a GIN index on `groups`, `sync_state` with a single-row CHECK, `client_mutations`, and `debug_items.archived_at`), `0005_seed_sync_state` (custom: the `sync_state` row at 0). All instants are `timestamptz(3)`. Sync scope per table and the `sync_groups` convention: `apps/server/src/db/README.md`.
> - **Repo (`apps/server/src/sync/repo.ts`)** replaces the PLAN-003 passthrough, which is deleted (it wrote synced tables without logging them):
>   - `insert`, `update`, `archive`, `unarchive`, `purge`, `changes()`, and `flush(origin)` → `{ lastSyncId?, lockedAt? }`. `update`/`archive`/`unarchive` lock the row and read its old groups first (`SELECT … FOR UPDATE`), write, then recompute groups with `groupsOf(row, tx)` (now async-capable, with the transaction) and store them if they changed.
>   - A groups change logs `D` (old groups) then `U` (new groups); `A`/`V` carry the full row. Both are new spec decisions (SPEC-002 Q4, Q5; sync-protocol §6 updated).
>   - `flush` with nothing buffered takes no lock. Otherwise: `pg_advisory_xact_lock(LOCKS.sync)`, `UPDATE sync_state … RETURNING`, one multi-row `INSERT INTO sync_log`. `data` is the row as JSON (camelCase keys, ISO timestamps with milliseconds, the full `syncGroups`). It is server-only; what clients receive is cut down per connection (SPEC-002 Q6).
>   - The executor uses `syncRepo` by default and records `surface_sync_lock_hold_seconds` (lock taken → commit) on the metrics registry.
> - **Operations:** `debug.create` (client-generated `id`, optional `groups`, default `workspace`), `debug.rename`, `debug.delete` (destructive), all internal, with handlers that check visibility first (invisible → `NOT_FOUND`). All four write ops, `debug.touch` included, now have `optimistic()` for session D's queue and overlay.
> - **AC-12:**
>   - **Static:** `surface/no-synced-table-writes` (`packages/config/eslint-rules/`, wired in `packages/config/eslint.js` for `apps/server/src/**` except `sync/repo.ts`) flags Drizzle `insert/update/delete` on a listed table, on anything taken from `SYNCED_MODELS` (also through a `const` alias or destructuring), and raw SQL that inserts into, updates, deletes from, merges into or truncates one. Raw SQL text is read from strings, `+` concatenations, templates (`${table}` counts as the table's name) and `sql.raw`/`sql.identifier`. A table passed in as a function parameter can't be seen statically; the runtime audit covers that. The table list `SYNCED_TABLES` lives in `packages/config/eslint.js`; `server/test/sync-lint.test.ts` (RuleTester) checks it equals `SYNCED_MODELS` plus `sync_log`/`sync_state`.

Queries are skipped (read-only). A test's own `checks` run after the audit, never instead of it. Gaps, documented in `test/executor.ts`: it matches by (table, id), and doesn't audit `sync_log`/`sync_state`.

> - **Notes for later slices:**

Apart from `syncGroups`, `data` is the client row shape; a model that gains a server-only column needs a projection here too.

### S3: Bootstrap endpoint · M · ✅ Done 2026-11-07
- `GET /sync/bootstrap`: a `REPEATABLE READ` transaction that reads `max(sync_id)` and streams `meta`, then the rows of every **eager** model filtered by `sync_groups && userGroups` (server-side cursors, 1,000 rows per fetch), then `end`. gzip via `@fastify/compress`.
- The server-side model registry maps synced models to their table, columns, and eager or content strategy. It is generated from the shared model definitions, to avoid duplicating them.
- **Tests:** snapshot consistency under concurrent writes (no row newer than `lastSyncId`), group filtering (AC-11, bootstrap part), throughput with 150k fixture rows.

> **As built (2026-11-07).**
> - **Versions:** no new packages. gzip uses `node:zlib`, not `@fastify/compress` as planned: one streamed route needs no plugin (CLAUDE.md: prefer the platform).
> - **Structure:**
>   - `sync/models.ts`: each synced model gains `def` (its `@surface/domain/model` definition) and `fixture`.
>   - `sync/registry.ts`: `syncRegistry({ includeFixtures })` builds `{ models, eager, schemaHash }`, with `schemaHash` = `computeSchemaHash` over the same definitions as the client. It maps each declared field to its column (snake_case, as Drizzle names it in SQL) and throws at startup when one is missing. `clientRow(model, row, rowGroups, visibleGroups)` gives declared fields only, instants as ISO with milliseconds, and `groups` = `sync_groups ∩ visible`.
>   - `sync/bootstrap.ts`: `bootstrapFrames(…)` is an async generator over one `REPEATABLE READ READ ONLY` transaction: `lastSyncId` from `sync_state`, counts, `meta`, a `DECLARE … CURSOR` per eager model with `FETCH 1000`, `end`. It always rolls back on an early close or an error, and destroys the connection if even that fails. It takes a narrow `BootstrapPool`, and selects groups and the archived flag under the aliases `__groups` and `__archived`, which no field can have (`defineModel` accepts camelCase names only).
>   - `sync/routes.ts`: `registerSyncRoutes` (`GET /sync/bootstrap`) reads the first frame before answering, so a database error is a `500`, not a cut-off `200`. It streams NDJSON (gzip when accepted) and sets `no-store`. Once the first frame is read, the response's `close` ends the transaction, so a client that hangs up at any point, even before the stream starts, releases its connection. Fastify logs a stream that fails after the headers went out.
>   - Wiring: `AppDeps.sync`, built in `server.ts` with `includeFixtures: nodeEnv !== 'production'`, sharing `resolveActor`. `signedIn` is now exported from `http/ops.ts` for both route sets.
> - **Spec decisions:** SPEC-002 §4.5 is new, with Q7 (API keys get `403`) and Q8 (the `groups` field convention; fixtures out of the production hash). sync-protocol §4.1 lists the errors, gzip and `groups`. `?groups=` (partial bootstrap) answers `400` until M7.
> - **Fix to S2 (D's S8 handoff):** `debug.create`'s `optimistic()` inserted `syncGroups` and `archivedAt`, which the client's `DebugItem` model doesn't have. It now inserts `groups`. Covered by `operations/test/debug-optimistic.test.ts`, which failed first.
> - **Review fixes (2026-11-07):** a client that hung up while rows were being counted leaked the pool connection inside an open transaction, because the stream's cleanup ran only once the stream had started. Multi-word fields mapped to the camelCase key instead of the snake_case column. The bootstrap aliases could in principle collide with a field. Q7 and Q8 were approved by the user.
> - **Tests:**
>   - `sync-registry.test.ts` (9): the hash equals the client's, fixtures are out in production, the column map, a multi-word field maps to its snake_case column (failed before the fix), the aliases can't be field names, a missing column is refused by name, the client row's shape (valid for `DebugItem.rowSchema` and the wire codec), groups cut to the connection, ISO instants.
>   - `sync-routes.test.ts` (11): `401`, `503` + `Retry-After`, `403` for an API key, `400` for `?groups=`, and `Accept-Encoding` parsing.
>   - `sync-hangup.test.ts` (3; a fake pool, a real HTTP server on 127.0.0.1): a client that hangs up while rows are counted gets the transaction rolled back and the connection released, plain and gzip; a full stream commits and releases. The plain case failed before the fix; gzip already passed, because `pipeline` destroys its source.
>   - `sync-groups.int.test.ts` (8, AC-11 bootstrap part; not held, leak test): decoded with the client's `NdjsonDecoder` and `decodeBootstrapFrame`. It checks that a user outside private team X gets none of X's rows nor another user's, a shared row arrives without X's group, and `meta.groups` holds only the actor's own groups. A member gets X's rows with X's group. `meta.rows` = `end.rows` = the row count, `lastSyncId` = `sync_state`, and the hash is the registry's. Rows pass `DebugItem.rowSchema`, the archived row is marked, gzip gives the same rows, and no transaction is left open. Planted bugs, each caught: no groups filter (2 tests fail), full groups sent (1), no archived flag (1).

### S4: Sync hub & WebSocket · L · ✅ Done 2026-11-07
- `LISTEN sync` on a dedicated connection. On notify, read new `sync_log` rows after `broadcastedUpTo` in order.
- Connection registry: `{ userId, clientId, groups, lastSentId, catchingUp, buffer }`.
- **Catch-up:** stream from `since` to the current `broadcastedUpTo` in pages of 500, buffering live packets for that connection, then flush the buffer and go live.
- Per-connection `prev` tracking. `ack` entries for the connection's own `clientId`. `resync` when `since` is outside retention or `schemaHash` differs. Ping every 25 s with a 10 s timeout. Close code `4001` on session revoke (exposed as `hub.closeSessions(sessionIds)` for PLAN-001).
- **Shutdown:** close all connections with `1012`.
- `synclog.prune` job (pg-boss, daily, 30-day retention).
- **Tests:** catch-up after 1,000 changes (AC-9), live-during-catch-up race, too-old and schema `resync` (AC-10, server part), group filtering on live and catch-up (AC-11), broadcast lag metric.

> **As built (2026-11-07).**
> - **Versions:** `@fastify/websocket` ^11.3.7 (on `ws` 8; the library ADR-0005 names), and `@types/ws` (dev, types only). No other new packages.
> - **Structure:**
>   - `sync/delta-writer.ts` (pure): `toPacket` and `DeltaWriter`, one connection's view of the log. It filters by the connection's groups, cuts `groups` to them (Q6), chains `prev`, cuts messages at 500 packets without ending one on a `D` whose row's packet follows (Q5), skips rows at or below what it has taken in (so overlaps are harmless), and sends acks only at a transaction boundary, on the last message (or alone).
>   - `sync/hub.ts` (`SyncHub`): `start()` listens, then takes the head as `broadcastedUpTo`. On notify it reads the head (`sync_state.last_sync_id`), then `(broadcastedUpTo, head]`, and delivers it synchronously, so every delivery ends at a transaction boundary and a connection registers either before or after it. `connect()` registers the connection and takes `upTo = broadcastedUpTo` in the same tick; live rows are buffered until catch-up of `(since, upTo]` finishes. Resync (`schema`, `too_old`) leaves the connection idle. Ping and pong, `closeSessions(ids)` → `4001`, `stop()` → `1012`. Catch-up waits while more than 1 MiB is queued on the socket (`#writable`, polled every 20 ms), for its pages and for the live rows buffered meanwhile; going live is synchronous with finding that buffer empty. Slow clients are dropped: a live socket with more than 8 MiB queued (terminated) or 50,000 buffered rows during catch-up (`1013`). A lost listen connection is closed and re-established with backoff (1 s doubling to 30 s), then the hub drains, since notifications sent meanwhile are lost but the log is not. Each ping round (25 s) also drains, so a listen connection that went half-open, or a read that failed, delays delivery by at most one interval; only notified deliveries count as broadcast lag, and a failed one keeps its notification time. `start()` closes its listener if reading the head fails. Metrics `surface_sync_broadcast_lag_seconds` and `surface_sync_connections` (via `useMetrics`, because the `/metrics` registry is built after the hub).
>   - `sync/hub-source.ts` (`pgSyncLogSource`): the hub's Postgres side behind the `SyncLogSource` interface. Catch-up reads pages of 500 with `groups && $groups OR client_id = $clientId` (the second half for acks only: those rows come back with `data` null and `groups` empty, so the writer finds nothing visible and sends only the ack). Each page is its own statement on the pool, followed by the retention check (`since` not ahead of the head, `min(sync_id) ≤ after + 1`); the prune deletes only a prefix and the oldest id only grows, so a check that passes after the read proves the page was complete. No connection or snapshot is held between pages, which matters because catch-up waits for slow readers (second review: one long `REPEATABLE READ` snapshot per catch-up let 10 slow clients hold the whole pool of 10, stalling writes, bootstrap and live delivery). The source's `pool` option is typed with `query` only, so a held connection can't come back by accident. `LISTEN` uses its own `pg.Client`, not a pool slot, with TCP keepalive and a 10 s connect timeout (`server.ts`); a client that fails to connect is ended.
>   - `sync/socket-route.ts`: `GET /sync/ws`. `preValidation` answers `503` (not ready, or hub not started), `403` (an `Origin` other than `SURFACE_URL`'s, checked before the session; or an API key, Q9) and `400` (connect parameters) over HTTP; a request without `Origin` (not a browser) is judged by its actor alone; no session is accepted and closed with `4001`. Binary frames close with `1003`; client messages are capped at 4 KiB. `sessionIdOf(request)` is optional until sessions exist.
>   - `sync/repo.ts`: `flush` queues `pg_notify('sync', last_sync_id)` in the `UPDATE sync_state … RETURNING` it already runs (no extra statement under the lock). `pruneSyncLog(db, before)` deletes the prefix of the log below the first row created at or after `before` (`created_at` is taken before the sync lock, so it is not strictly in id order, and deleting every old row could leave a hole that `min(sync_id)` hides), and always keeps the newest row, which the retention check relies on.
>   - `jobs/index.ts`: `synclog-prune`, daily at 03:41, 30-day retention.
>   - Wiring: `server.ts` builds the hub unless `SURFACE_ROLE=worker`, starts it after migrations and before `markReady()`, and stops it in the `connections` shutdown phase.
> - **Spec decisions:** SPEC-002 §4.3 now states the notification, delivery boundaries, catch-up snapshot, who may connect, limits, retention and shutdown. New decisions: Q9 (API keys get `403` on the socket, as on bootstrap) and Q10 (`since` ahead of the head → `resync(too_old)`). The §10 metric is renamed `surface_sync_broadcast_lag_seconds` (Prometheus base units, like the lock-hold metric). sync-protocol §4.3 lists the extra close codes and refusals; all of them are "reconnect with backoff" for the S7 client, unchanged.
> - **Bug found while checking by hand:** the log reads selected `sync_id::text AS sync_id`, so `ORDER BY sync_id` sorted the text ("10" before "9"), and the writer then rightly dropped the rows that came out of order: a catch-up of 1,050 rows delivered 54. The alias is now `id_text`. The AC-11 test seeds more than ten log rows so its exact-ids check fails on that bug (it did, before the fix).
> - **Tests:**
>   - `sync-delta-writer.test.ts` (14): `prev` chain and 500-packet messages, groups filtered and cut, A/V/D as ids, the `D` rule (and a lone `D` for a user who lost the row), partial messages held mid-range, overlaps and rows at or below `since` skipped, unknown models skipped, acks once per mutation on the last message, ack-only messages, acks wait for the boundary, never another client's acks.

### S6: Client store: models, pool, IDB · L · ✅ Done 2026-11-06

> **As built (2026-11-06, session D):**
> - **Deps:** `mobx` ^7.1.4 and `idb` ^8.0.4 in sync-client; `zod` ^4.6.7 in domain (session A adds the same line); dev: `fake-indexeddb` ^6.2.7, `fast-check`, `@types/node`.
> - **Model definitions** live in `packages/domain/src/model/` and are exported as the subpath **`@surface/domain/model`** (so `domain/src/index.ts`, owned by A, is untouched). Builders `uuid() str() int() bool() timestamp() enumOf([...]) json() array(item)` plus `.nullable()`. `defineModel(name, { load, fields, refs, indexes })` adds the implicit `id`, validates names, refs and indexes, builds a Zod `rowSchema` (it strips undeclared columns such as `sync_groups`), and returns a `ModelDef` that `computeSchemaHash` accepts directly. The definition is frozen all the way down, except the Zod schemas. Field and ref names that would shadow instance members (`toJSON` and the `Object.prototype` names) are rejected. Canonical type names are part of the hash: `uuid`, `string`, `int`, `bool`, `timestamp`, `json`, `enum<a|b>` (members sorted; `|`, `<`, `>` and duplicates rejected), `array<string>`. Fixture: `DebugItem { title, counter, groups: string[] }`, indexed on `title`, in no production model list.
> - **Instances (deviation from "MobX observable instances"):** MobX 7 dropped `{ proxy: false }`, so `observable()` objects are always Proxies. Instead each model gets a generated prototype with one getter per field, backed by a MobX atom created on first read and released when unobserved. That gives per-field reactivity, no proxy traps, and near-zero cost for unobserved rows. **ADR-0015** (accepted 2026-11-06) supersedes ADR-0003's "enforced by MobX strict mode" clause. Instances are frozen and getter-only, rows are deep-frozen as they enter base or overlay, and views get a type-level `ReadonlyPool` (`SyncStore.pool`). The package exports only `SyncStore`, `rowOf`, the errors and types, pinned by `test/public-api.test.ts`. No global `configure()` is set. Fields are not own properties: use `toJSON()` / `JSON.stringify`, not `Object.keys` or spread. Instance identity is stable across updates. `$model` and `$archived` are meta getters.
> - **Pool (`ObjectPool`):** each entry holds `base` (server only), `overlay` (`undefined` = none, `null` = optimistically deleted), and the visible instance. The API: `applyBase(changes)` (upsert, archive, unarchive, delete), `loadBase`, `sweepBase`, `setOverlay` (for S8), plus reactive reads `get`, `all`, `count`, `findBy(model, field, value)`, `ref`, `backRef`. Passing a definition (`pool.get(DebugItem, id)`) types the result. Each write is one `runInAction` batch. Archive and delete of unknown ids are ignored, and an upsert keeps the archived flag.
> - **Indexes:** `Map<value, Set<id>>` per field with a lazy atom per value, so a lookup re-runs only when its own bucket changes. A `backRef` auto-indexes the target field. Only scalar fields are indexable, and `null` is a key.
> - **Storage (`SyncStorage`):** `IndexedDbStorage` (stores `meta`, `pending` and `row:<Model>`; a model-list change bumps the DB version and rebuilds row stores, keeping `pending`; an upgrade blocked by a stubborn old tab rejects with "Close other Surface tabs and reload" instead of hanging; a connection closed by another tab's upgrade or by the browser fails with `StorageClosedError` saying to reload; `readRows` pages on keys, so an unreadable record doesn't end paging), `MemoryStorage` (E6 fallback), and `serveStorage` / `connectStorage` RPC over any message port, with `storage/worker.ts` as the module worker entry. The RPC never hangs. The worker gets 10 s to open (then start-up falls back to memory) and 30 s per call. Worker `error` and `messageerror` events and `close()` fail pending and later calls with `StorageUnavailableError`. `close()` terminates the worker. `openStorage` tries worker → same-thread IDB → memory: a worker that cannot be created or fails (CSP, load error, open timeout) falls back to IndexedDB on the main thread (`connectWithFallback`), and only a missing or failing IndexedDB means memory. **Multi-tab safety (E5), not in the plan:** a per-bootstrap *generation* fence (writes from a stale generation throw `StorageFencedError`), per-row *version* = the sync id that wrote it (older deltas are skipped), *tombstones* for deletes, and `lastSyncId = max(...)`. `applyChanges(generation, changes, lastSyncId)` is implemented and tested for S7 to call. Bootstrap writes use `durability: 'relaxed'`.
> - **Persistence:** two kinds of failure are kept apart. A *fenced* generation (another tab re-bootstrapped) ends only this tab's row writes for that generation, via `writeReplica(generation, …)` and `isCurrent(generation)`. Storage stays usable for pending mutations and no warning shows, because the other tab persists the same data. Any other failure (quota, closed DB, dead worker) *loses* storage and shows an observable `storageWarning`. The memory fallback is written to like any storage (so S8's pending queue works there) but is never `persistent`. Rendering is unaffected either way.
> - **Bootstrap / warm start / store:** `bootstrap()` reads the body with the S1 `NdjsonDecoder` and validates frame order, `schemaHash` (`ClientOutdatedError`), every row against `rowSchema` (errors name the field, never the value), and `rows` counts. It writes chunks of 1,000 to storage and the pool, reports progress, and marks the replica `ready` only after `end`. On re-bootstrap it sweeps base rows the server no longer sent and keeps overlays. It cancels the download on abort or bad data. `hydrate()` pages 1,000 rows per model from storage, re-reads `meta` at the end and gives up if the generation changed meanwhile, then sweeps pool rows the replica lacks. `SyncStore` (`start()` → `'warm' | 'cold'`, `resync()`, `close()`, observable `status`, `progress`, `position {lastSyncId, groups, generation}`, `persistent`, `storageWarning`) uses `replicaName = surface-<workspaceId>-<userId>`. `start` and `resync` run one at a time. `close()` aborts whatever is running and waits for it to settle (a start never reports `ready` after close), then closes storage, resets `status` to `idle` and clears `position` and `progress`; the pool keeps its rows until the next `start` replaces them, and `start()` may be called again. **Cross-tab start-up (E5), not in the plan:** with Web Locks (`navigator.locks`, injectable as `locks`), a warm start holds the replica lock shared and a bootstrap holds it exclusive, re-checking the replica first. A second tab therefore waits for a bootstrapping tab and then warm-starts, and two fresh tabs bootstrap once. Web Locks need a secure context. On plain HTTP, tabs start unlocked: the fence keeps the replica consistent, but two tabs starting together may both bootstrap (documented in `locks.ts`).

### S7: Socket client & delta apply · M · ✅ Done 2026-11-06
- WebSocket lifecycle with backoff (0.5 s to 30 s, jitter), the `online` event, and ping/pong.
- **Delta apply:** strict order, `prev` gap check that triggers a reconnect (E1), ignore `id ≤ lastSyncId` (E2), upsert/archive/delete into base, IDB persist (batched per message), and a `lastSyncId` update.
- Handling of `resync` (re-bootstrap while keeping the pending queue) and close code `4001` (emit `session-revoked`).
- **Tests:** a gap triggers a reconnect, duplicates are ignored, resync keeps pending mutations (AC-10, client part).

> **As built (2026-11-06, session D):**
> - **No new dependencies.** The transport is the platform `WebSocket`, behind a `SocketFactory` seam.
> - **`src/socket.ts` (`SyncSocket`):** dials `ws(s)://<baseUrl>/sync/ws?since&clientId&schemaHash`, built at each dial so `since` is current. States are `disconnected | connecting | online | offline | revoked` (observable as `store.connection`). It answers `ping` with `pong`. A connection silent for 35 s (ping interval + timeout) is dropped. Backoff: a ceiling doubling from 1 s to 30 s with the delay drawn from its upper half (0.5–1 s first, 15–30 s at most). It resets only after a healthy message (a ping or applied deltas), so a server that accepts and then drops connections isn't hammered. The `online` event redials at once. Close `4001` stops for good and calls `onSessionRevoked`, also on a connection that never opened; `retryLater()` does not undo it. Any other close reconnects with backoff. A malformed or binary frame drops the connection and retries. A gap (E1) also reconnects through the backoff, so it costs 0.5–1 s (more if the backoff has not been reset): acceptable for a rare event, and it keeps a server that keeps sending gaps from being hammered. The `onOpen` option tells the store the server is reachable again. Transport, timers, randomness and the online source are injected (`SyncStoreOptions.connection`); tests use `ManualTimers` and never sleep.
> - **`src/deltas.ts` (`planDeltas`):** `prev > lastSyncId` is a gap: nothing is applied and the socket reconnects with `since = lastSyncId` (E1). Otherwise packets with `id ≤ lastSyncId` are skipped (E2) and the rest applied. Every row is validated before anything is applied; a bad row drops the connection. A `G` packet triggers a full resync (until M7). **Doc clarification (no wire change):** sync-protocol.md §4.3 now spells out the `prev ≤ lastSyncId` case, which the old text ("apply only if `prev` equals") left as a reconnect.
> - **Store:** `start()` connects once ready, and `resync()` stops the socket, re-bootstraps and reconnects from the new position. A `deltas` message is applied to the pool at once (one MobX batch), `position.lastSyncId` moves, and the storage write (`writeReplica(generation, applyChanges(…))`, one per message) goes through the store's serial queue, so it never interleaves with a resync and `close()` waits for it. `resync(too_old|groups)` re-bootstraps. No deltas apply during a resync: it stops the socket as its first queued step (a start queued before it may have connected in between), and `#receive` answers `pause` unless `status` is `ready`. If a resync fails, the socket retries with backoff and the store runs the resync again when the next connection opens (`onOpen`); it does not wait for the server to ask again. `resync(schema)` and a `ClientOutdatedError` move `status` to the new **`outdated`** value (the reload banner, E7), with no reconnect. `close()` stops the socket first, and again inside its queued task. A start or resync that finishes after a `close()` (e.g. while the replica lock is being released) rejects as aborted and does not connect. `start()` on a running store does nothing and resolves with how it started. A row that fails validation in a delta makes the client reconnect; after 3 rejections at the same `lastSyncId` it re-bootstraps. A resync whose snapshot has a bad row (`ProtocolError`) is not retried: `status` goes `failed` (SPEC-002 E12). The new observable **`store.error`** holds the message of the last failed start or resync, for the inspector.

> - **`store.dispatch(op, input)`** (`src/queue.ts`, `MutationQueue`): refuses queries, parses the input with the operation's schema, checks the wire shape (`mutationSchema`, JSON only) and the size (UTF-8 bytes of the encoded mutation, at most 90 % of the 1 MiB body limit), and throws `InvalidInputError` before anything is queued. It copies the input (`structuredClone`), assigns the next seq, shows the optimistic effect **synchronously** (AC-5), persists the entry, and returns a promise of the outcome (`confirmed`, or `rejected` with the server's `code` and `message`). It throws before `start()`, after `close()`, when the client is `outdated` ("Reload the page"), and when the queue was taken over ("Reload this tab"). Observable: `store.pending` (`seq`, `op`, `at`, `state`: `queued | sent | committed`), `store.rejections` (the last 20), `store.clientId` (the queue's). Options: `operations` (the registry; default `@surface/operations`), `onRejected` (called after the rollback; a throwing handler cannot break sync), `onOutdated` (called once on every path to `outdated`: mutate 426, `resync(schema)`, a bootstrap from a newer server), `clock`.
> - **Lifecycle (sync-protocol.md §4.4, §5.1):** an entry is sent only once it is persisted. One batch is in flight at a time, in seq order, up to 100 mutations or 90 % of the body limit in UTF-8 bytes. `ok` records `lastSyncId = N` (persisted); the entry is confirmed when the replica reaches N, when an `ack` for its seq arrives (before or after the response, live or in catch-up), or **at once if the replica has already passed N** when the response arrives (a resend after a reload, answered from the server's record). `error` removes the entry, rebuilds the overlay, then calls `onRejected`. A `413`, or a `400`/`422` with a readable error body, halves the batch until the mutation at fault is alone, then rejects it locally (`PAYLOAD_TOO_LARGE` or the server's code); the skipped seq then triggers a `SEQ_GAP`. A network error, 5xx or unreadable body retries the same batch with the socket's backoff. A request with no answer after 30 s (`REQUEST_TIMEOUT_MS`), or in flight when the socket drops, is abandoned and resent (deduped); when the socket is back the queue sends at once, dropping any pending retry delay. `CLIENT_OUTDATED` stops the queue and the socket. `SEQ_GAP` renumbers every mutation after `lastSeq`, committed-but-unconfirmed ones included (their `lastSyncId` is cleared), in one storage write; an answer that leaves nothing to renumber backs off.
> - **Deviation, flush order:** the queue flushes as soon as the socket opens (and the store is `ready`), not after catch-up. The protocol has no "caught up" signal, and none is needed: confirmation waits for the replica to reach each commit. SPEC-002 §3.6 and sync-protocol.md §5.3 updated; approved by the user.
> - **Queue ownership (`src/owner.ts`, SPEC-002 E5):** each queue is a `clients` record (`clientId`, `nextSeq`, `owner`, `leaseUntil`) plus its `pending` entries (key `[clientId, seq]`) in the replica database. A tab sends only the queue it owns; a queue left by a closed or reloaded tab is adopted, so its mutations are resent under the same `(clientId, seq)` (E3, E4). With **Web Locks** the owner holds `<replica>:queue:<clientId>`; a start tries the queues with work waiting first, then the others by id, then a new one. Without them (plain-HTTP origins, or `locks: null`) a **lease** is renewed every 5 s and lapses after 15 s. A start adopts only a lapsed queue *with pending mutations* (an empty one may belong to a frozen tab), and each renewal of a tab whose own queue is empty adopts one too, then lets its empty queue go: a reload, which cannot end its lease on the way out, picks its queue up within 15 s. Empty queues that were released, or whose lease ended over a day ago, are forgotten at the next claim. Every claim writes a per-tab `owner` token, every queue write checks it (`QueueFencedError`), and the claim returns the queue's entries in the same transaction. A tab that loses its queue starts a new one if it had nothing pending; otherwise it stops (socket too) with `status = failed` and "Another tab took over the changes waiting to be sent. Reload this tab.", which a bootstrap finishing later cannot override; `start()` again claims a new queue. Switching queues redials the socket, since acks are addressed to the connection's `clientId`. A `clientId` is used for one queue only: a new queue never reuses an id a previous start may have sent under (the server would answer seq 1 with an old result). The memory fallback has nothing to share and always starts a new queue. `storage.clear()` (re-bootstrap) keeps both stores.

Each mutation runs in its own layer: if `optimistic()` throws or writes a row its model rejects, that layer is dropped and the others stand. References in `optimistic()` resolve against base plus the mutations before them (never the screen), so a replay is deterministic. `push` applies one new mutation on top (the dispatch path); `rebuild` starts again from base, on a confirm or reject, on warm start (after hydrate, before `ready`), on adopting a queue, and when a delta touches a row any pending mutation read or wrote, or any row of a model one searched by name. ## 5. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Overlay recomputation is too slow with many pending mutations offline | Recompute only touched IDs. Benchmark 1,000 pending mutations offline. Coalesce consecutive same-field updates in the queue (safe because they are idempotent intents). |
| A catch-up or live race causes missed packets | Per-connection buffer during catch-up, a `prev` check on the client, and dedicated tests with injected delays |
| IDB write throughput limits the cold bootstrap | Worker with large chunked transactions, a strict-durability flag off where supported, and the progress UI. Measured in the nightly perf run. |
| The serialized sync-log lock contends under bulk operations | A bulk op is one transaction with one lock. Hold time is a metric. Revisit only if p95 > 5 ms. |
| Simulation tests are flaky | Deterministic seeds, fake timers in the network layer, and no real sleeps |
